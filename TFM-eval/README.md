# bpmn-eval

Automated BPMN 2.0 diagram quality evaluation pipeline for a Master's Thesis. Compares diagrams generated by LLMs via two approaches — **zero-shot** (direct XML generation) and **DSL** (custom textual DSL compiled to XML) — across ten reference-free metrics.

## Metrics

### Scored metrics (0.0–1.0)

| ID | Name | What it measures |
|----|------|-----------------|
| M1 | XML Validity | Schema conformance against BPMN 2.0 XSD |
| M2 | Structural Connectedness | Graph reachability & ID integrity |
| M3 | Element Degree | In/out-degree constraints per element type |
| M4 | Gateway Executability | Default paths & conditionExpressions on diverging gateways |
| M5 | Label Completeness | Ratio of elements with a non-empty `name` attribute |
| M8 | Gateway Matching | Every split gateway has a strictly type-matched join where all branches reconverge |

### Descriptive metrics (values in `details`, `score` pinned to 1.0)

| ID | Name | What it reports |
|----|------|-----------------|
| M6 | Size | Total Number of Nodes (TNN = tasks + events + gateways) and Total Number of Sequence Flows (TNSF) |
| M7 | Control-Flow Complexity (CFC) | Cardoso's CFC: sum over diverging gateways (XOR=n, OR=2ⁿ−1, AND=1) |
| M9 | Coefficient of Network Complexity (CNC) | Density ratio TNSF / TNN |
| M10 | Cyclicity | Presence, count, and member nodes of cycles in the control-flow graph |

All scored metrics are normalized to [0.0, 1.0]. Descriptive metrics (M6, M7, M9, M10) pin `score = 1.0` and `passed = None`; their raw values live in `MetricResult.details` so they don't distort aggregate score means. No ground-truth reference models are required.

## Setup

```bash
pip install -e ".[dev]"
```

**Python 3.11+ required.** Only runtime dependency is `lxml>=5.0`.

## Usage

```bash
# Evaluate all cases, output JSON + CSV
bpmn-eval data/ --schema-dir schemas/ -o results/ --format both

# JSON only
bpmn-eval data/ --schema-dir schemas/ -o results/ --format json

# Check a single case
bpmn-eval data/cases/case_001/ --schema-dir schemas/
```

## Evaluating tracked experiments (tfm-lab)

`bpmn-eval` above compares zero-shot vs DSL per `data/cases/` case. To instead
score the **tracked experiments** produced by the tfm-lab app
(`EXP-<process>-<sys>-<provider>-<model>-R<NN>/`), use `bpmn-eval-experiments`.
It evaluates each experiment's `diagram.bpmn` (or the XML embedded in its
`result.json`) and writes a per-experiment report aggregated by process, model,
provider, system-prompt version, and run:

```bash
bpmn-eval-experiments \
    --experiments ../apps/tfm-lab/prompts/experiments \
    --schema-dir schemas/ \
    -o results/experiments \
    --format both
```

Output `results/experiments/results.csv` has one row per experiment: the five
provenance axes + `status` + the 10 metric scores + descriptive values
(`tnn`, `tnsf`, `cfc_total`, `cnc_value`, `has_cycle`). Runs whose DSL failed to
compile appear with score `0.0` (the failure rate is itself a result). Metrics
are semantic-only, so this step never requires rendering — but generate the
`diagram.bpmn` files first with the tfm-lab render step (or run the repo-root
orchestrator `scripts/run-evaluation.ps1`, which does both).

## Checking .bpmn file quality

To evaluate how good your BPMN files are:

1. Place them in `data/cases/<case_name>/` as `zero_shot.bpmn` and/or `dsl.bpmn`.
2. Run `bpmn-eval data/ --schema-dir schemas/ --format both`.
3. Inspect the terminal table for per-case scores or open `results/results.csv` in Excel/R.

Each metric score tells you:
- **M1 = 0.0** → the XML does not conform to the BPMN 2.0 XSD (parse errors, missing required attributes).
- **M2 < 1.0** → some nodes are unreachable from the start event or flow references broken IDs.
- **M3 < 1.0** → some elements violate degree rules (e.g., a task with no incoming or no outgoing flow).
- **M4 = 0.0** → diverging gateways have no default path or conditions on outgoing flows.
- **M5 < 1.0** → proportion of unnamed elements (tasks, gateways, events lacking a `name`).
- **M8 < 1.0** → some split gateways have no matching converging gateway (branches end at different endpoints or a wrong-typed join) — indicates a broken block structure.
- **M6, M7, M9, M10** → open `results/results.json` and read `.details` for raw TNN/TNSF, CFC total, CNC, or cycle lists; compare distributions across zero-shot vs DSL.

## Repository structure

```
TFM/
├── src/bpmn_eval/
│   ├── metrics/          # M1–M5 implementations
│   ├── parsing/          # BPMN XML parser & namespace helpers
│   ├── pipeline.py       # evaluate_case() / evaluate_all()
│   ├── comparison.py     # Aggregate statistics
│   ├── reporting/        # JSON, CSV, and stdout reporters
│   └── cli.py            # CLI entrypoint
├── schemas/              # BPMN 2.0 XSD files (OMG spec)
├── data/cases/           # Test cases (case_NNN/)
├── tests/                # pytest test suite
└── results/              # Output directory (git-ignored)
```

## Adding a new metric

1. Create `src/bpmn_eval/metrics/new_metric.py` with a dataclass satisfying the `Metric` Protocol (`name`, `description`, `evaluate(model) -> MetricResult`).
2. Add one line to `ALL_METRICS` in `src/bpmn_eval/metrics/__init__.py`.
3. Add tests + fixture `.bpmn` under `tests/`.
